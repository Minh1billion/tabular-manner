Engine reference

Tabular Manner

Tabular Manner is a graph-based engine for data processing workflows. A pipeline is described as a JSON graph of nodes and connections; the engine validates it, compiles it into an execution graph, and streams lifecycle events as it runs on top of Polars.

spec -> validate against the registry and sandbox -> compiled node graph over Polars LazyFrames -> execution runtime -> event stream

Overview

A pipeline is a named JSON document with two top-level arrays: nodes and connections. Each node wraps one registered node type; connections wire node outputs to node inputs, optionally through a named input slot.

Nodes

Each entry has an id, a type naming a registered node, a display name, and a params object with the node's configuration.

Connections

Each entry has a from id and a to id, and optionally into (which input slot to fill on a fan-in node such as join).

Any node with no incoming connection is treated as an entry point; a graph needs at least one. Execution starts at every entry point and fans out along the connections until every branch reaches a node with no outgoing connection, called a leaf.

Getting started

The engine is assembled once with build_engine(), which wires together storage, the node registry, and the execution runtime into a single Engine object.

from tabular_manner.engine.bootstrap import build_engine
import json

engine = build_engine()

# a pipeline is just a JSON graph of nodes and connections
with open("pipeline.json") as f:
    spec = json.load(f)

for event in engine.execution.execute(spec=spec):
    print(event["event"], event.get("data", ""))

Every call on the engine's APIs returns an iterator of event dictionaries rather than a single value. Each event has an event name and a ts timestamp; the terminal event is either completed (with a data payload) or failed (with an error message). This gives callers a consistent, streamable shape across validation, execution, resource management, and node registration.

Execution

Compiles a graph spec and runs it, or re-runs a graph already compiled in a previous call. Accessible as engine.execution.

execute(execution_id=None, spec=None, bucket=None, cancel_check=None)

Iterator[dict] execute(execution_id: str | None, spec: dict | None, bucket: str | None, cancel_check: Callable[[], bool] | None)

Provide spec to validate, parse, and run a new graph in one call, or pass a previously returned execution_id to re-run an already-compiled graph against a fresh context. Exactly one of the two is required. bucket is only used when compiling from spec; it is ignored when re-running via execution_id, since the graph was already compiled against whatever bucket was active at that time.

bucket does two things. First, it selects which node registry the parser resolves type against: custom node types registered through NodeLibrary.register_transform(..., bucket=...) are only visible to graphs compiled with that same bucket (omitting it uses the default registry). A type that exists in another bucket still fails validation as an unknown node type. Second, for any node whose type binds resource_storage from context and accepts an optional bucket param (fetch_internal, push_internal), execute's bucket is copied into that node's own params.bucket whenever the spec didn't already set one. An explicit bucket in a node's params always wins over this default.

Cancelling a run

cancel_check is an optional zero-argument callable returning a bool. When provided, execute calls it once before traversal starts and again before every node in the graph, in order:

  • Before injecting context, right after the graph is resolved (whether just compiled or recalled via execution_id). If it returns truthy here, no node ever runs.
  • Before each step of graph.traverse(...), and again before every node_progress update reported by a batched sink, so a long-running export can be interrupted between row batches rather than only between whole nodes.

The first truthy check yields a single cancelled event and returns, without yielding completed. Either way, a cancelled execution's compiled graph is dropped from the cache, so its execution_id can no longer be reused with execute(execution_id=...).

# typical wiring: a threading.Event flipped by whatever cancels the job
cancel_event = threading.Event()

for event in engine.execution.execute(spec=spec, cancel_check=cancel_event.is_set):
    if event["event"] == "cancelled":
        break
No cancel_check, no cancellation. When it's omitted, execute runs straight through to completed or failed; the check is only ever consulted if you pass one in.

validate(spec, bucket=None)

Iterator[dict] validate(spec: dict, bucket: str | None)

Checks a spec against the registry and sandbox without compiling or running it. bucket scopes the node registry the same way it does for execute, so a graph using bucket-specific custom node types must be validated with that same bucket to resolve them. Yields validating followed by either valid or failed.

Unlike execute's failed event, which only carries the single error that stopped compilation, validate walks the whole graph and, when the failure comes from node params, connection wiring, or schema inference, attaches an errors array to the failed event with one entry (node_id, node_type, message) per problem found, not just the first. Structural failures (unknown node type, bad connection reference, no entry point, a cycle) still short-circuit as a single error.

discard(execution_id)

None discard(execution_id: str)

Drops a compiled graph from the cache so it can no longer be reused with execute(execution_id=...). Called automatically on cancellation; can also be called directly to free a graph you know you won't re-run. Compiled graphs are also evicted automatically, oldest-used first, once more than max_cached_graphs (see build_engine, default 128) are held at once - so a long-idle execution_id can become invalid even without an explicit discard.

Node Library

Custom node types are looked up by the parser the same way built-in ones are, so once registered they can be used as any other type value in a graph spec - provided that graph is compiled with the same bucket the type was registered under (default bucket if omitted on both sides). A name is global to its bucket: it cannot collide with a built-in type or with another custom type in the same bucket, but the same name can be reused independently in a different bucket.

A node type produced by register_transform is not called with zero configuration: at graph-build time it still requires a columns param (list of column names), and applies expression to each of those columns independently, with the target column's own value bound to the identifier value (in place of the whole-row df used by filter/derive). See Sandbox for what an expression is allowed to contain.

Operator parameters

Every node in a graph spec configures itself through a flat params object. The node's type decides which keys make sense, and the engine checks them before anything runs, using the same handful of rules everywhere.

Required vs optional

A required param must be present and correctly formed, or the graph fails validation before it runs. An optional param falls back to a fixed default when it's left out, so most nodes can be configured with only a handful of keys even though they support more.

Typed, not just present

Every param has an expected shape: a plain type such as string, integer, or boolean, or a typed list such as a list of strings. A value of the wrong shape fails validation the same way a missing required value does.

Beyond that, a handful of param shapes recur across many node types and mean roughly the same thing wherever they show up:

ShapeTypical meaning
columnsWhich column or columns a transform reads or rewrites. Most numeric, text, and missing-data transforms take this.

a mode string, such as how, keep, method, or if_table_existsPicks one strategy out of a short, fixed set of names; an unrecognized value fails validation instead of silently falling back to a default behavior.
a mapping object, such as types, mapping, or aggregationsPairs a column name with a per-column instruction: a target dtype, a replacement value, or an aggregation function.

Some params exist to control the engine's own behavior rather than the shape of the data, such as schema on source nodes (see Source and sink nodes) or chunk_rows and progress_threshold_rows on sinks that can batch their output.

Sandbox

Two node types, filter and derive, take a string expression instead of a fixed set of params. So does a transform type registered through register_transform. None of them run that string as ordinary Python; each one is parsed and checked against a fixed grammar before it's allowed anywhere near a graph.

The check runs when a graph is parsed or validated, not while it's running, so a disallowed expression is rejected before any node executes rather than partway through a pipeline. Three rules do the actual gatekeeping:

Only two names exist

A filter or derive expression can only reference df (the whole row) and pl (Polars). A registered transform uses value in place of df, since it runs per target column rather than against the whole row. Any other identifier is rejected.

Attribute access is an allow-list

Calling something off pl only works for a small set of column-building helpers. Chaining a method off a column expression only works for a small set of aggregation and conditional helpers. Anything starting with an underscore is rejected outright, and so is anything not on either list.

The grammar itself is narrow: arithmetic, comparisons, boolean operators, conditionals, and method calls made through attribute access are allowed; assignments, imports, loops, comprehensions, lambdas, and bare function calls are not.

What's allowed in practice

AllowedExample
Column referencedf.amount
Column functionspl.col("amount"), pl.lit(1)
Conditional expressionpl.when(df.amount >= 150).then(pl.lit("high")).otherwise(pl.lit("low"))
Arithmeticdf.amount * df.quantity
Comparisonsdf.amount >= 100
Method calls on columnsdf.amount.mean()

Anything outside this set - imports, arbitrary function calls, attribute access on anything other than df/value or the narrow set of pl helpers - is rejected before the graph ever runs.

and / or pass the grammar check but don't combine column conditions. The grammar lets and, or, and not through, but each side of a comparison like df.amount > 0 evaluates to a Polars Expr, and Polars raises TypeError: the truth value of an Expr is ambiguous as soon as such a value is used in a boolean context - which is exactly what evaluating and/or/not does. A filter or derive expression that combines two column conditions this way (for example df.amount > 0 and df.quantity > 0) passes validation but fails at execution time with that error. The bitwise equivalents Polars normally recommends for combining expressions (&, |) are not in the allowed grammar either, so there is currently no working way to AND/OR two column-based conditions in a single expression. and/or/not only work here on non-Expr values, such as plain Python constants.

register_transform (see Node Library) reuses this same sandbox, with a value identifier standing in for the target column's own value in place of the whole-row df.

The role of Polars

Every node ultimately reads or rewrites a Polars LazyFrame. The engine supplies the graph, the wiring, the validation, and the event stream; Polars supplies the table engine underneath all of it.

Lazy by default

A source node opens a lazy scan rather than reading data immediately. Every transform and merge node adds another step to that lazy plan without touching real data. Nothing is actually computed until a sink collects the result, or the compiler needs to peek at a schema.

Schema without materializing data

Validation infers the columns and types flowing out of a node by asking Polars for the lazy plan's schema, which resolves names and dtypes without running the plan. A source can skip this and declare its schema up front instead, for cases where sampling the real source isn't possible or worth the cost.

Dtypes are Polars dtypes

Wherever a graph names a type, in cast's types or a source's schema, it's naming a Polars dtype directly, such as Int64 or Float64. There is no separate type system to translate between.

Batched collection for large sinks

A sink that supports progress reporting can ask Polars to hand back the result in row batches instead of one collected table, which is what makes it possible to write a large export incrementally and report progress as it goes.

Because every node speaks the same LazyFrame, chaining nodes together costs nothing beyond building the plan: a ten-node graph and a one-node graph both do zero actual work until something forces a collection.

Source and sink nodessourcesink

Sources start a branch by reading data in; sinks end a branch by writing data out. Both types read and write lazily.

schema. Every source node except fetch_internal accepts an optional schema param: an object mapping column name to Polars dtype name (the same format as cast's types, for example {"amount": "Float64"}). When set, it is used as-is for schema inference and validation instead of sampling the actual source, which is useful when the source isn't reachable yet at validation time or when inference would be expensive. It does not cast or affect the data read at execution time - only the schema the compiler assumes for downstream nodes.

fetch_internal is the one exception, and not by accident: it reads a resource the engine itself already wrote (via push_internal or import_source), stored internally as Parquet - a format that carries its own schema, so there's nothing to declare and nothing to sample remotely. The other five sources read something outside the engine's control (a file that may not exist yet, a bucket, a live database) where the schema either isn't knowable in advance or is expensive/impossible to check during validate, which is exactly what schema is for.

Batched exports and node_progress. push_internal, push_csv, push_parquet, and push_arrow can write their output in row batches instead of one call. chunk_rows sets how many rows go into each batch. progress_threshold_rows sets the row count at or below which the sink skips batching entirely and writes the whole result in a single pass, since progress reporting isn't worth the overhead for a small result. Batching only applies when the destination supports being written incrementally; when it doesn't, the whole result is written in one pass regardless of size. Whenever a sink does batch its output, the engine reports a node_progress event after each batch with the rows written so far. When the destination is S3, batches are uploaded incrementally as a multipart upload, so progress advances steadily instead of jumping straight to 100% at the end. If a batched export is interrupted partway through, for example by cancellation, the partial output is discarded rather than left behind as a corrupt file.

Connection fields

FieldDescription
from / toNode ids being connected.
intoInput slot to fill on the target node. Required for fan-in nodes with named inputs, such as join's left and right.
onWhich output port of the from node to read. Defaults to "out", the only port any built-in node exposes, so it can be omitted for every node type documented here; it exists for custom node types that declare more than one output port.
Entry points, and no cycles. Any node with no incoming connection starts a branch when the graph runs. A graph must have at least one; a graph with none fails validation. Validation also walks the connection graph for cycles independently of the entry-point check, so a loop anywhere - even one that still leaves other nodes reachable from a valid entry point - fails validation with the offending cycle's node path in the error message.

Ports and merging

Every built-in node has a single output port, so connections never need to pick a port on the way out. A node's output can still feed more than one connection - that's how a branch fans out to several downstream nodes.

Fan-in nodes work the other way: instead of choosing an output port, incoming connections choose an input slot. union accepts any number of branches on the default port and concatenates them. join requires exactly two, matched to its left and right input slots via each connection's into field.

Common patterns

A few small shapes cover most graphs: a straight line, a fan-out, and a merge.
